# Program-fit evidence map

This is a factual mapping for maintainers preparing an application. It is not a statement that the repository is eligible, selected, or entitled to a grant.

| Program signal | Evidence the repository can show | Gap at launch |
|---|---|---|
| Active open-source project | Public-ready repository, CI, release artifacts, maintainer docs, contract-lock workflow | Public maintenance history is new |
| Meaningful usage / adoption | GitHub Action, CLI, SARIF, Harbor bridge, benchmark adapters | External users are not yet established |
| Clear ecosystem importance | Evaluator decision-boundary testing, release assurance, frozen-candidate attribution, contract lock | External validation is still the highest-value missing signal |
| Active maintenance | PR-oriented CI, release gates, issue/PR templates, versioned changelog | Real external PR/issue history must be earned |
| Core OSS work | The tool is itself OSS evaluation-maintenance infrastructure and can run locally | None technically; actual adoption matters |
| API credit use | Bounded semantic escalation for ambiguous/high-risk maintainer changes, with recorded request/token usage | Actual API usage should be generated by real maintenance work, not fabricated |

## Selection strategy

Do not optimize the repository around the grant. Optimize for a maintainer seeing immediate operational value:

`lock evaluation contract -> change evaluator -> changed-surface detection -> deterministic boundary tests -> optional semantic escalation -> evidence/SARIF -> review -> update lock`

The strongest missing evidence is external: an independent benchmark or evaluator maintainer should run the workflow and confirm that the findings are useful.
